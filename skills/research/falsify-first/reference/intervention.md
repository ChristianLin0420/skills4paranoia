# 變更規格與 diff 的規矩

第 4 題的產出。先寫規格，確認之後才碰 code。

## 規格的四個欄位

```
介入        動哪個模組、具體改什麼
必須不變    列出來。這一欄比上一欄重要
驗證斷言    什麼檢查能證明介入真的生效
順帶改變    這個介入不可避免地還改了什麼
```

### 「必須不變」要具體到可檢查

不要寫「其他都不變」。要寫：encoder 權重、資料前處理路徑、optimizer 與 LR schedule、seed 協定、評估腳本 —— 逐項列出，跑完之後可以逐項確認。

一個實驗最常見的失效方式不是介入做錯，是**順手動了別的東西**。

### 驗證斷言要在訓練開始的前幾百步就能跑

例子：

```
ablate 世界模型   assert wm.parameters() 的 grad 全為 None 或 0，且 forward hook 未被觸發
凍結 encoder      assert 訓練前後 encoder 權重雜湊相同
換掉預訓練資料    assert 實際載入的 task id 集合 == 預期集合，樣本數相符
縮小模組          assert 總參數量 == 預期值 ± 0
```

**沒有斷言的介入不要跑。** 這跟 `vla-code-review` 抓的是同一類病：`requires_grad=False` 擋不住 BatchNorm 更新，你以為凍結了其實沒有。

### 「順帶改變」要誠實

移除一個模組同時減少了參數量、改變了梯度尺度、可能改變了有效學習率。這些不是 bug，但它們是結果的替代解釋，必須寫下來，並且在解讀時考慮進去。

如果順帶改變太多，這個介入就不乾淨，回頭找別的操作。

## 產 diff 的規矩

規格確認之後問：「要我直接改 code 嗎？」得到明確同意才動手。然後：

**一、先確認 branch。** 絕不直接改主訓練路徑。沒有 branch 就先開一個。

**二、diff 只能包含介入本身與它的驗證斷言。** 進到 code 裡一定會看到別的可以改的地方 —— 不要碰。夾帶進來的話結果就無法歸因，你不知道變化來自介入還是那個順手修好的 bug。順手的修正另開 commit，而且要講出來。

**三、驗證斷言跟介入寫在同一個 diff 裡。** 不要留待之後補，之後就不會補了。

**四、改完印出「必須不變」清單的實際狀態**，讓人一眼確認沒有動到不該動的。
