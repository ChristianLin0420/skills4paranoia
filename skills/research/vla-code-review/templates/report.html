發現 — 依嚴重度排序

阻斷4.4 多卡訓練時 action head 的梯度沒有跨 rank 同步 train.py:388
症狀
不會報錯。多卡與單卡的 loss 曲線看起來幾乎一樣，但多卡的最終表現不如預期，且卡數越多差距越大。
成因
action head 被 DistributedDataParallel 包起來，但程式呼叫的是 action_head.module.predict_action(...)。繞過 DDP.forward() 會讓 reducer 沒有被註冊，反向時梯度不會 all-reduce。每個 rank 只用自己的 local batch 更新自己的頭。
怎麼確認
訓練幾步後比較兩個 rank 上 action head 參數的雜湊值。同步正常時必須相同。
修法
呼叫 action_head(...) 而不是 action_head.module(...)；把 predict_action 的邏輯移進 forward()。
同型案例：moojink/openvla-oft#160 — OpenVLA-OFT 的 finetune.py 有完全相同的問題。
阻斷10.5 checkpoint 載入失敗時回傳未訓練的模型而不是拋錯 policy/loader.py:64
症狀
呼叫看起來成功，沒有例外，回傳的是正常的 policy 物件。唯一線索是一行捲上去的 warning。
為什麼致命
任何「把載入的模型跟自己比」的驗證都會通過，因為兩邊都是同一個未訓練模型，數字會完美吻合卻毫無意義。整批量測可能在你發現之前就已作廢。
怎麼確認
載入後比對權重雜湊與 checkpoint 檔的雜湊；或斷言載入後 missing_keys 與 unexpected_keys 皆為空。
修法
載入失敗一律 raise。要容忍缺鍵就顯式列出允許缺的鍵名，不要用寬鬆的預設。
同型案例：huggingface/lerobot#4577 — PI0Policy.from_pretrained 即使 strict=True 也會回傳未訓練模型。
高2.1 純 bf16 訓練，沒有 fp32 master weights train.py:118
症狀
訓練後期停止進步，但 grad norm 看起來完全正常。容易被誤判為方法飽和。
成因
bf16 相對精度約 2^-8。當 |lr × grad| / |w| < 2^-8 時更新加上去權重不變，被靜默丟棄。後期權重變大、梯度變小，此條件很容易成立。
怎麼確認
抽樣參數，統計 optimizer.step() 前後完全未改變的比例。超過個位數百分比就是問題。
修法
改用 AMP（預設保留 fp32 master weights），或在 optimizer 內加 stochastic rounding／Kahan 補償求和。
同型案例：Physical-Intelligence/openpi#989 — 同資料同協定下 JAX 混合精度 82.6 vs PyTorch 純 bf16 71.9。
高6.8 評估時整個 suite 共用一個 env，episode 之間場景幾何會漂移 eval/run_eval.py:148
症狀
同一個 checkpoint 重跑兩次分數不同；episode 序號越後面越不穩。
成因
env.seed() 只在建 env 時呼叫一次，RNG 串流會跨 episode 前進。env.reset() 從該串流取樣家具擺位並寫進 sim.model.body_pos，而 set_init_state() 只還原 qpos／qvel，不還原 body_pos。
怎麼確認
連續兩個 episode 之間 diff sim.model.body_pos。應為零。
修法
在 episode 迴圈內呼叫 env.seed(cfg.seed)，或每個 episode 重建 env。
同型案例：openvla/openvla#342 — LIBERO 評估中爐台在 episode 之間位移 3.0mm。
高9.1 沒有梯度裁剪，且沒有記錄 clip 前的 grad norm train.py:214
症狀
訓練中途 loss 突刺後崩潰，之後永不回復。輸出退化成與觀測無關的固定動作。
為什麼重要
VLA 的 LoRA 微調對這個特別敏感，一次突刺就足以讓整個 run 報廢，而你要跑完才會發現。
修法
加 clip_grad_norm_；同時記錄 clip 前與 clip 後的 norm。只記 clip 後的話它永遠等於閾值，看不出任何前兆。
同型案例：openvla/openvla#333 — LoRA 微調在第 6000 步 loss 由 2.2 跳到 5.2，成功率歸零且不回復。
中6.4 動作正規化統計沒有與 checkpoint 綁在一起 data/stats.py:23
症狀
換了資料版本之後推論的動作幅度不對，但訓練指標完全正常。
修法
把 mean/std 存進 checkpoint，推論時從 checkpoint 讀。啟動時斷言統計的雜湊與訓練時一致。
同型案例：moojink/openvla-oft#156、openpi#1025（社群要求加正規化相容性報告）。
觀察6.7 成功判準可能過寬，需要你判斷 envs/tasks/place.py:88
看到什麼
成功條件是物體中心進入目標框且速度低於閾值，但沒有要求夾爪已鬆開，也沒有保持幀數要求。
為什麼提出
這類判準在別的 benchmark 上被證實會高報：物體還在夾爪裡、或即將掉落時就已判定成功。我無法判斷你的任務是否可接受，所以標為觀察而非發現。
建議
加保持幀數（例如連續 10 幀）與夾爪狀態條件，然後重跑一次舊 checkpoint，看分數掉多少。掉很多的話，過去的數字都要重新解讀。
同型案例：SimplerEnv#129（WidowX 任務過度樂觀）、LIBERO#149（物體接觸桌面前即判成功）。
