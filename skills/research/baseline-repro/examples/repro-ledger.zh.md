# 復現 — Kestrel-VLA 對我們的重實作

**判定。** 我們在量別的東西。**我們自己**的 eval harness 有兩條慣例解釋掉整個落差；方法本身復現得出來。
論文 63.2% · 我們量到 51.4% · 落差 11.8pp · 改兩個常數就回收 10.5pp

**Scope。** 只測一條 claim：Table 3，"ours, 7B, fine-tuned"，TaskSuite-40 平均成功率 63.2%。
不測他們的訓練配方、資料，或那張表的其他任何一列。

## 什麼解釋掉這個落差

兩條平凡的慣例疊在一起。**兩者都不是錯誤，也都不戲劇化**——而這正是常見的形狀，
也是「他們的數字灌水」不該是第一個假設的原因。

| 因素 | 他們 | 我們 | 關掉的成本 | 回收 |
|---|---|---|---|---|
| Episode 上限 | 400 步 | 300 步 | 一個常數 | 4.8pp |
| Chunk 執行方式 | 每步重新規劃 | 8 步開迴路放完 | 一個迴圈 | 5.7pp |
| | | | | **10.9 中的 10.5pp** |

**Episode 上限。** 我們的 harness 把每個 policy 都卡在 300 步，好讓跨模型比較一致。
任何超過 300 步才成功的 rollout 被靜靜改判成失敗，而 Kestrel 的 policy 比我們自家 baseline 慢，
所以這個 cap 對它的懲罰比對我們重。

**Chunk 執行方式。** 他們預測 8 個 action、執行 1 個就重新規劃；我們 8 個全部執行完才重新預測。
同樣的權重、不同的控制器——第 2 步就滑掉的抓取，開迴路重放救不回來。
**這一條在任何 config 裡都沒有痕跡。** 它活在 rollout 迴圈的形狀裡，diff config 永遠找不到。

## 關掉它們

| | |
|---|---|
| 第 ② 格基準 | 51.9% |
| ＋ episode 上限 300 → 400 | 56.7% |
| ＋ 改成每步重新規劃 | **62.4%** |

62.4% 對上他們的 63.2%，而 ① 是 62.8%。剩下的 0.8pp 落在三個 seed 的散佈裡，不需要解釋。

## 哪裡容易 · 哪裡困難

**容易** — 權重跟 code 都有釋出，第 ① 格才跑得起來。他們的 eval 進入點只吃一個 checkpoint 路徑。
`pip freeze` 第一次就對上。

**困難** — 真正有影響的那兩條軸**都是「缺席」**：論文沒寫的 episode 上限，
以及論文跟 config 都沒有的執行模式。兩條都是把他們的 rollout 迴圈跟我們的並排讀出來的，
**沒有任何工具會產出這種 diff**。下一次請直接編半天給這個閱讀。

## 這件事的影響超出那一個數字

那兩條慣例**都是我們自己 harness 的家規，不是錯誤**——而且它們套用在這套 harness 跑過的每一個模型上。
我們內部發表過的每一次跨模型比較，都帶著同一個 300 步 cap 跟同一種開迴路執行，
而兩者都一致地懲罰比較慢的 policy。**當成家規站得住腳，當成沒寫出來的家規則不然。**

我們會發現這件事，只是因為剛好有一次比較的對象是公開數字加公開權重。**否則不會有任何東西讓它浮出來。**
